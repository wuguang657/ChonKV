# 生产级差距与路线图：这套 Raft 离 etcd/TiKV 还差什么

> 时间：2026-09-07
> 范围：对 `src/raft`、`src/kvraft`、`src/labrpc`、`src/raft/persister.h` 实测后，
> 评估当前 MIT 6.824 C++ 移植版（已完成 Lab 2A/2B/2C/2D + Lab 3 KV-Raft）与
> 生产级 Raft（etcd / TiKV / Consul 一类）之间的结构性差距，并给出落地路线图。
> 所有"缺失"结论均来自实际 grep / 读码，非推测。

---

## 〇、结论先行

这套实现是**教科书级正确**的，甚至有几处比原版 lab 更生产化（T2/T3 快照窗口双层防护、
异步 RPC + cancel、动态线程池、exactly-once 去重、porcupine 线性化校验）。

但它仍是 **"单集群、固定成员、内存持久化、模拟网络"** 的实验室版本。离生产级差 4 个方向：

1. **真实持久化**（Persister 现在纯内存）
2. **集群成员变更**（Raft 状态机里完全没有任何运行时增删节点逻辑）
3. **读路径优化**（Get 走了一遍日志，没有 ReadIndex/Lease）
4. **真实传输层**（labrpc 是软件模拟，无流控/TLS/背压）

## 二、核心缺口（分档）

### 🔴 Tier 1：不补就不叫"生产级"

**1. 持久化是假的——这是接下来要亲手写的部分**
- 铁证：`persister.h` 全篇是内存 `std::string raft_state_` + 一把锁（`persister.h:23-71`），
  **没有任何文件 I/O、没有 fsync、没有 WAL、没有校验和**。
- 生产要求：state + snapshot 落盘（`pwrite` / `fsync`），**批量 group-commit**
  （不能每条 persist 都 fsync，否则吞吐崩），断电后靠 CRC 校验 + 原子 rename 双文件
  （state 文件 + snapshot 文件）防半截写。自研 kv-engine 的 POSIX `pwrite/fsync` 经验正好平移。

**2. 集群成员变更——缺这一个就不是"分布式系统"**
- 铁证：grep `AddServer|RemoveServer|membership|joint` 命中**全部是 `net_->AddServer`
  的静态拓扑搭建**（`raft/config.cpp:267`、`kvraft/config.cpp:129`），
  **Raft 状态机里没有任何运行时增删节点逻辑**。
- 生产要求：Raft 论文 §6 的 joint consensus，或 Ongaro 单步成员变更
  （每次只加减 1 个节点，新旧配置都算多数）。etcd / TiKV 靠它在线扩缩容。
  这是实验室版最大的结构性缺失——Lab 4 ShardedKV 用"分片迁移"绕过了它，
  但**真正的 Raft 集群扩缩容没有**。

**3. 读路径：Get 走了日志，没有 ReadIndex / Lease**
- 铁证：`server.cpp:173` Get → `WaitOp` → `rf_->Start(op.Serialize())`（`server.cpp:213`），
  即**每个读都当一条日志提交**。
- 生产要求：ReadIndex（leader 先确认自己仍是 leader 的 commitIndex，再直接读本地状态机，
  不写日志）或 Lease Read（Leader 在租约内直接读）。etcd 默认 ReadIndex——
  生产 KV 读延迟从"一次 Raft 提交"降到"一次网络 RTT"的关键。

### 🟠 Tier 2：强烈建议，否则扛不住真实流量

**4. Pre-Vote（预投票）缺失**
- 铁证：grep `prevote|PreVote` 零命中。
- 风险：一个被网络分区、带着 stale term 的节点恢复后，会疯狂自提选举、把 term 推高、
  打断现任 leader 心跳，造成抖动。生产版（etcd）一律加 Pre-Vote：
  先问"你们愿意投我吗"，拿到足够回应才真增 term。

**5. 快照是单个大 blob，没有分块流式传输**
- 铁证：`InstallSnapshotArgs.data` 是一个 `std::string`（`raft.h:168`）；
  `EncodeSnapshotLocked` 一次性编出整块（`server.cpp:101`）。
- 风险：状态机一大，一条 InstallSnapshot RPC 传几 MB~几百 MB，期间持锁/占连接，集群卡顿。
  etcd 用分 chunk 的 snapshot 消息（带 `index / term / offset / recvId`），流式边收边写。

**6. AppendEntries 没有批处理 + 流水线**
- 现状：复制是"一次一个 entry"的发射后不管（`raft.h:357` inflight_log_ 在途标志）。
- 生产：把多个 entry 打包进一条 AppendEntries，并 pipelining（不等上一条 ack 就发下一条）
  隐藏 RTT。吞吐从"1/RTT 条"到"N/RTT 条"的量级提升。

**7. 传输层是 labrpc 模拟，不是真实网络**
- 铁证：`labrpc.*` 是丢包 / 延迟 / 乱序的**软件模拟**，双线程池、cancel 机制都很精致，但：
  无 flow control、无消息大小上限、无 TLS、无连接池 / 背压、无真实 TCP 重连语义。
- 计划"自己写 RPC"对应这一层：要补 gRPC / TCP 化 transport——流控、msg size limit、
  TLS、连接复用。

### 🟡 Tier 3：运维成熟度（决定"能不能上线"）

| 缺口 | 说明 |
|---|---|
| Leadership transfer / 优雅下线 | 重启 / 缩容一个 leader 时，先主动让位，避免选出新主的空窗抖动 |
| Learner / Witness 节点 | 加新节点先当 learner（不算多数、不投票）追上日志再转正，否则拖慢整个集群 |
| 可观测性 | 现在只有 `fprintf(stderr,...)` 排错日志（`server.cpp:345` 等）；生产需要 metrics（commit latency / 吞吐 / apply lag）、tracing、结构化日志 |
| 形式化验证 / 混沌测试 | 没有 TLA+ 模型、没有 Jepsen / chaos 注入、没有确定性仿真；测试靠 `test_raft.cpp` 但不穷尽 |
| 并发粒度 | Raft 用**单把大锁**（`raft.h:295` mu_）；KV 锁与 Raft 锁交叉顺序靠人工维护（`server.cpp:251-255` 注释反复强调"不能持 KV 锁跨进 raft 锁"），脆弱且高争用；生产用更细粒度 + 独立 transport / apply 线程 |
| 快照节流 / 磁盘空间管理 | 触发条件是 `RaftStateSize() < maxraftstate`（`server.cpp:150`），无频率节流、无磁盘水位保护 |

## 三、从实验室到生产的路线图（结合已有计划）

| 步骤 | 动作 | 收益 / 对接点 |
|---|---|---|
| 1 | **写真 Persister**：内存 → `pwrite/fsync` 双文件 + CRC + group-commit 批刷 | 最小、最独立、最体现存储功底，直接对接 XSKY / 百度面试（用户已计划） |
| 2 | **写真 RPC transport**：替换 labrpc 为 TCP/gRPC 化层，带流控 / msg-size-limit / TLS / 背压 | 复用已设计的 `ReplySlot` / `cancel` / `CallAsync` 模型（用户已计划） |
| 3 | **加 ReadIndex**：Get 从"走日志"改为"leader 确认 commitIndex 后直读" | 吞吐 / 延迟质变，面试高频题 |
| 4 | **加 Pre-Vote**：改动小、收益大，消除分区节点干扰 | 一行选举前置，稳定性质变 |
| 5 | **加单步成员变更**：集群在线扩缩容 | "分布式存储系统"硬门槛 |
| 6 | **快照分块流式**：大状态机必做 | 避免大快照卡集群 |
| 7 | **批处理 + 流水线**：AppendEntries 打包 + pipeline | 吞吐优化 |
| 8 | **TLA+ 验证 + chaos 测试**：正确性从"测试通过"升级到"可证明" | 把正确性做成可证明资产 |

## 四、给面试的"一句话定位"

> 我这套 Raft 实现了论文 Figure 2 全部机制 + 日志压缩 + 线性化 KV，并通过 porcupine
> 验证了线性一致性；它和 etcd 这类生产系统的差距主要在四块——**真磁盘持久化（含 fsync
> 批刷与崩溃恢复）、在线成员变更、ReadIndex 读优化、真实带流控/TLS 的传输层**——
> 而这四块恰恰是我接下来要自己动手补齐、并把 kv-engine 的存储经验平移进来的地方。
